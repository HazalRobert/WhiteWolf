一、确认的原始错误及原因
用户提供的最初错误为 SCHEMA: Missing pagination cursor。代码中该错误由控制器的分页结果校验产生。
旧版解析器允许非空、无空白和控制字符、最长 4096 的不透明游标；控制器及下一页请求入口却另外限制为 Base64 风格字符、最长 2048。两个合同不一致。
公开真实 Following 响应的 Bottom 游标为 1771337970390780275|2085474368099450818。竖线被旧规则拒绝；因此“Missing”并不意味着服务端缺失这个字段。
新版将控制器与请求入口改为同一校验函数，并通过测试确认它与可序列化解析器的合同相同。不拆分、不解码、不裁剪、不改写游标；下一页仍通过 JSON 和 URLSearchParams 编码传递。
我们未读取用户当次具体游标，不能声称拿到了用户的原始响应。证据是相同错误路径、独立公开响应、修复前后完整浏览器回归。

三、官方机制核对与实际修正
Chrome 文档说明，空闲服务工作线程通常在30秒后结束；Chrome114起打开Port本身不再重置空闲计时器，实际Port消息才会延长其生命周期。
https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle
因此新版只在有效控制会话中保持心跳；取消、错误、断线及窗口关闭都清理计时器。后台真正终止时仍停止处理，不自动重连、重发或续跑。

旧版后台遇到SCHEMA停止会话，却让控制Port继续存在。稍后断开事件将原SCHEMA覆盖为WORKER_RESTART。该行为已在联合单元测试及实际隔离MV3后台强制停止测试中复现。
新版错误回复明确标记会话已结束，界面先关闭连接再呈现原错；后续断开不会覆盖它。页面关闭/重载、权限撤销、会话替换分别带明确信息。无法确认原因的控制断开不再一概宣称后台已经重启。

四、验证范围
pagination-regression.json：旧版1.1.5同错；新版1.1.6完成两页，游标原样送达第二页，0次关系写入。
lifecycle-before.json / lifecycle-after.json：原错保留与实际后台停止；新版还经过65秒控制连接空闲观察。
浏览器自动化可能影响自然休眠。初次65秒旧版观察没有自然复现休眠；后续用CDP仅在独立合成测试浏览器主动停止后台，不能把这说成用户Chrome自然休眠实测。
browser-report.json：实际MV3后台、页面脚本、解析器与UI的隔离回归；包含十语言布局、手动/自动模式、白名单与模拟关系操作。
所有X流量均在测试内截获，未访问用户真实账号、未执行真实关注或取关。真实账号重载后的扫描尚未验证。这些是1.1.6历史验证范围说明；历史报告和本机路径未随公开仓库分发。1.2.2的当前构建与测试方法见根目录README.md。
